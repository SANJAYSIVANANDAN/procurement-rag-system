# ADR-021 — Chat orchestration: decisions made while building M11

**Status:** Accepted (V1)

The design is fixed by the spec (§22, §26, ADR-005, ADR-011): a LangGraph `chat_graph` whose nodes are thin, tokens that originate in the graph, a producer task that outlives the HTTP request, and a Redis lock that allows one reply at a time per conversation. These are the decisions the spec left open or where the implementation differs.

- **Graphs never import `db`.** An import-linter contract forbids it, so the caller's `OwnershipScope` travels through graph state as an opaque value (`Scope = Any` in `graphs/deps.py`) and only the ports and engines look inside it. Everything that reaches PostgreSQL goes through `ChatPersistencePort`, implemented by `services/chat_persistence.py` with one unit of work per call. Memory and retrieval are ports too (`MemoryPort`, `RetrieverPort`), so the graph's unit tests run with no database and no Redis.
- **One `retrieve` node, not `retrieve_hybrid` and `rerank`.** `RetrievalEngine.retrieve` already runs hybrid search, reranking with its fallback to the fused order, and parent expansion as one operation with one trace. Splitting it into two nodes would mean exposing the engine's internals to the graph for no gain. The stage the user sees is `searching`; the trace records whether reranking ran or was skipped, and why. `assess_evidence` also builds the numbered context, since the verdict depends on it.
- **Citation events are emitted by `finalize`, after the commit (spec 26.7), not by `validate_citations` (spec 22.4's table).** The two sections disagree; 26.7 states the reason (whatever a client sees as final must already be durable), so `validate_citations` only computes and `finalize` stores and then emits.
- **Order inside `finalize`:** PostgreSQL commit, then the Redis window (best effort: a failure drops the session so the next load rebuilds it), then `citation` events, then exactly one of `message_complete` or `error`. A failed message is stored with the text streamed so far and is not recorded in memory.
- **A stream always starts with `message_start` and ends with exactly one terminal event, whatever happens.** The runner validates every event against the models in `streaming/events.py`, stamps the message id, drops anything after a terminal event, and opens the stream itself (`seq: 0`) if the run failed before it began. If the graph ends without a terminal event (a bug, a crash), the runner stores the message as failed and publishes `INTERNAL_ERROR`. On cancellation (shutdown) it marks the message `interrupted` and publishes `INTERRUPTED`, shielded from the cancel. Tests assert the order after every scripted run.
- **Failures are mapped to words a user can see, never to provider text.** `graphs/errors.py` turns an exception into `(code, safe message, retryable)`; the detail goes to the log. The model failing before the first token is retried by the provider wrapper (twice, with backoff); after a token, nothing retries (it would repeat visible text) and the message ends `failed` with the partial content and `retryable: true`. A refusal, a truncated answer and a rejected request are not retryable.
- **The classifier and the rewriter fail soft.** Routing a question is not worth failing it over: if either call fails (provider down, refusal, output that is not the schema) the question is treated as a question about the documents and searched as written. The answer call has no such fallback. Cheap cases are decided by rules with no model call: a greeting, or a named clause or section.
- **Abstention is a template, streamed.** Weak or no evidence, or no documents selected, never calls the model. If the model did answer but no citation survives validation, the draft that was streamed is replaced on `message_complete` by the abstention (spec 26.6: the client replaces the draft with `content`).
- **Draft answers are stripped before validation.** A streamed answer ends with whitespace the model emitted; the final content is the validated, trimmed text.
- **The lock comes first, and ownership comes before the lock.** `ChatService.submit` checks the conversation is the caller's (404), answers a repeated `client_message_id` from what is stored (200, no lock, no model call, even while another reply is being written), then takes the lock (`SET NX EX 120`, random token, Lua compare-and-delete release and extend, heartbeat every 30 s), then stores the pair. Checking ownership first means a stranger gets a 404 and never a 409 that would reveal the conversation is busy. Redis down is a 503 with nothing stored. Any failure after the lock is taken releases it; so does the producer's `finally`.
- **The producer's references live on the service, not at module level.** The spec says a module-level set; an instance attribute holds the tasks just as well, and lets tests and shutdown ask one service what it is running (`idle()`, `aclose()`).
- **Shutdown.** `aclose` waits up to 20 s for replies in flight, then cancels the rest, which marks them interrupted and tells their listeners. The stale-message sweeper (every 60 s, safe from every replica at once because it only touches messages past 10 minutes) covers the case where the process was killed outright.
- **The production container publishes to a `NullPublisher` for now.** The Redis Streams publisher and the consumer endpoint are M15 (spec 36); an in-memory publisher in a long-running process would keep every event forever. Until M15, the reply is read from `GET /conversations/{id}/messages` when it is `completed`. The 202 response already carries the `stream_url` the M15 endpoint will serve.
- **Prompts are versioned files** (`chat_answer.v1.md`, `classify.v1.md`, `rewrite.v1.md`); the summary prompt from M10 keeps its name, `conversation_summary.v1.md`, instead of the spec's `summarize.v1.md`. Source text and the conversation summary are declared data in every prompt, and the answer prompt is told to ignore instructions inside sources.
- **The Anthropic adapter** (`ai/llm/anthropic_provider.py`): no `temperature`, `top_p` or `top_k` (current models reject them), no `thinking` parameter (the model thinks adaptively), `output_config.effort` from the route, the server-side refusal fallback on, `stop_reason` checked before content is used, the SDK's own retries off (the wrapper retries), and errors that never carry prompt text or a key. Tests use the SDK's own transport with real SSE frames; the spec names `respx`, but the installed SDK sits on `httpx2`, which `respx` does not patch. The live tests (`tests/e2e/test_anthropic_live.py`) are opt-in and have not been run: there is no key on this machine.
- **A fix to M10 found here.** Rebuilding a window from PostgreSQL included the question being answered (its message is `completed` while its reply is still `pending`), so recording the finished turn added it a second time. A window now holds only exchanges whose reply completed; a failed or interrupted exchange is not memory.
- **`covenantiq migrate` also creates the LangGraph checkpoint tables** (`AsyncPostgresSaver.setup()`, idempotent). The chat graph does not use them (ADR-005); the analysis graphs will, from M12. The tables are outside Alembic, so the migrations round-trip test is unaffected. On Windows psycopg's async mode needs the selector event loop, which the helper selects.
- **Not built:** the SSE consumer and Redis publisher (M15), per-user chat cost limits, `Regenerate` as its own endpoint (it is a new submission with a new `client_message_id`), and comparison questions requiring every named document to contribute (the evidence assessor supports it; the graph does not yet name documents).
