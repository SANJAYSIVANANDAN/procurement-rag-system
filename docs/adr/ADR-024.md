# ADR-024: Evaluation harness: decisions made while building M14

**Status:** Accepted (V1)

The design is fixed by the spec (§28): a versioned dataset with checksums, custom deterministic metrics, RAGAS for the LLM-judged ones, an offline run that gates CI and a full run that reports. These are the decisions the spec left open, or where what was found differs from what it says.

- **The dataset is generated, and its labels follow from how it was generated.** `eval/datasets/generate_v1.py` assembles each contract from a clause library with controlled variants (good, problematic, ambiguous, absent) and derives the questions, passages, findings and vendor expectations from the same library entries. A label cannot disagree with its document, a contract that lacks a clause really lacks it, and unanswerable questions are exactly those about absent topics. The output is committed; the generator is the record and is deterministic (a test regenerates it and checks nothing changes). The cost: contracts are short and regular, so the dataset is easy compared with real agreements, and the numbers say nothing about real ones.
- **Documents are plain text, not PDF or DOCX.** The offline run must be deterministic and cheap, and Docling takes minutes and downloads models. A small `TextExtractor` maps the text format (`@page N`, `# ` headings, numbered paragraphs) to the same `RawItem`s Docling's adapter produces and hands them to the production `build_blocks`, so clause references, the quality gate, chunking and embedding are the real code. What is not exercised offline is Docling itself (covered by the slow suite).
- **No CUAD or other public set in v1.0.0.** The spec lists it as optional. Importing one means a licence review and a mapping from its categories to the rule ids; it is left for a later dataset version, and the manifest records that all sources are project-owned.
- **Manifest checksums are enforced at load.** Any changed, missing or unlisted file refuses to load, with the instruction to regenerate. A baseline additionally records the manifest's own hash, so a regenerated dataset with the same version string cannot be compared to an old baseline unnoticed.
- **Findings labels cover every rule that applies to the contract type**, not a hand-picked subset: a rule the contract has no clause for is labelled `absent`. This makes risk precision and recall well defined, and it made the first run find something: `DP-001` ("data protection terms") was labelled absent in contracts that contain a personal-data breach clause, and the system answered `insufficient_evidence` because the taxonomy tags that clause as data protection and the spec forbids claiming absence while a clause of a matching type exists. The system was right and the labels were wrong, so the dataset now gives those contracts a data protection section. This is the kind of disagreement the harness is for; it was resolved by correcting the labels, not by weakening the rule.
- **The scripted model tests the safety net, not a polite model.** For an answerable question it writes the labelled answer and cites the sources that contain the labelled passage (or the top source if retrieval missed). For an unanswerable one it fabricates a confident, unsupported claim. The claim and marker metrics are therefore computed only over answerable questions; abstention metrics use all. The rule-assessment oracle answers from the labels *only when the labelled clause is among the passages it was shown*, so a retrieval miss appears as a finding error rather than being papered over.
- **Metrics are ratios over examples with a bootstrap interval.** Each example contributes a numerator and denominator, the value is the sum of numerators over the sum of denominators, and the 95% interval resamples examples with a fixed seed (1,000 resamples). An example with a zero denominator is not counted in `n`. Where `n` is small the intervals are wide and the report shows it.
- **Retrieval metrics use the passage text, not chunk ids.** A retrieved chunk "is" a labelled passage if their token Jaccard is at least 0.5, as the spec defines for citations. Non-LLM context precision and recall use normalised Levenshtein similarity with RAGAS's threshold of 0.5, implemented here (so the offline run needs no RAGAS) and left to RAGAS in the full run.
- **Determinism is checked, not assumed.** The offline run is the gate, so it must reproduce itself exactly: a second run matched the baseline on every metric (a test repeats this on a micro dataset). The scoring determinism metric also runs the vendor scoring three times on identical input.
- **The gate judges direction.** The tolerance is an allowed move in the *worse* direction (a fall for higher-is-better, a rise for lower-is-better); a move in the better direction never fails, and a metric that disappears, becomes unmeasurable, or a run with errors fails. Vendor scoring determinism has tolerance 0.
- **A deliberate regression the spec names does not trip the gate.** Raising the RRF constant to 1,000 changes no metric on this dataset, because the reranker orders the final candidates. The regressions the tests use are the ones that demonstrably move the numbers (returning one passage; refusing everything with over-strict evidence thresholds). If the RRF constant matters, a run with the real reranker is where it will show.
- **The full run is built and has never run.** `run_full.py` uses the configured real providers, refuses fake ones (a "full" report from fakes would be a fabricated one, spec 28.1), asks before spending, runs the same pipeline and custom metrics, then RAGAS's six metrics through `eval/ragas_adapter.py`, and prints the spec 28.7 targets next to what was measured. The adapter presents our model and embedding providers to RAGAS and is tested with fakes (the judge calls our provider, the embeddings are ours, which answers are judged). No RAGAS metric has been computed with a real judge. RAGAS 0.4.4 is pinned in an optional `eval` dependency group so the runtime image does not carry LangChain; `from ragas.metrics import ...` is deprecated there and will need `ragas.metrics.collections` before RAGAS 1.0.
- **Evidence-threshold calibration (task 6) was not done.** It needs a real embedding model and reranker. The offline run shows the gate misjudging both ways with the fake ones (it refuses 15.5% of answerable questions and passes 40% of unanswerable ones), which says the thresholds depend on the reranker's score scale, not what they should be.
- **Not built:** `make eval-retrieval` (real embeddings and reranker, fake model, report only), vendor extraction stability over three live assessments, and the committed full report under `docs/eval/`. The first two need provider keys; the third needs the full run.
