# ADR-017 — A local cross-encoder reranker in its own process

**Status:** Accepted (V1, optional provider)

- **Decision:** `CIQ_RERANK_PROVIDER=cross_encoder` reranks with `cross-encoder/ettin-reranker-150m-v1` (Apache 2.0, English only, 150M parameters, loaded with sentence-transformers). The model runs in a separate process and container (`covenantiq rerank-serve`, Compose service `reranker`, profile `rerank`). The API and the workers talk to it over HTTP (`RemoteReranker`) and never import PyTorch; a unit test fails if loading the application loads `torch`, `transformers` or `sentence_transformers`.
- **Why a separate process:** a cross-encoder is CPU-bound. In the API it would stall the event loop; in a worker it would compete with Docling extraction. As its own container it has its own CPU and memory limit, restarts independently, and can move to a GPU host by changing only `CIQ_RERANK_URL`.
- **Protecting the rest of the system:**
  - Scoring runs in a thread, one request at a time, so the service's own event loop (health checks) stays responsive.
  - More than 3 requests in flight or queued are answered `503` at once instead of queueing past the caller's budget.
  - The caller sends its deadline; the server scores in batches of 4 (shortest passages first, least padding) and stops between batches when the deadline passes (`504`), so work nobody will read does not occupy the CPU.
  - The client keeps the fused order on any failure (spec 19.8) and, after three failures in a row, skips the call for 30 seconds, so a slow or dead reranker costs the application nothing.
  - The service has no database, broker or API keys, and never logs the text it scores (only counts and timings).
- **Scores:** the model returns raw, unbounded relevance scores (about -3 to 14). The client maps them with a sigmoid into (0, 1), which keeps the order. The evidence thresholds in spec 19.10 (0.55, 0.35, 0.30) were written for Voyage scores and **must be recalibrated** for this model before the evidence gate relies on them; `RemoteReranker.rerank_raw` returns the raw scores for that.
- **Measured speed (this repository's 350-token chunks, 30 passages, CPU only):**

  | Setup | Time for 30 | Pairs/s |
  |---|---|---|
  | fp32, 4 threads | 21.8 s | 1.4 |
  | fp32, 8 threads | 10.5 s | 2.9 |
  | fp32, 16 threads | 8.8 s | 3.4 |
  | **in the container**, 4 CPUs | 20.8 s | 1.4 |
  | **in the container**, 8 CPUs (default) | 11.9 s | 2.5 |
  | **in the container**, 12 CPUs | 10.2 s | 2.9 |
  | **in the container**, 16 CPUs (all) | 19.7 s | 1.5 |
  | int8 dynamic, 16 threads (bypassing sentence-transformers) | 6.1 s | 4.9 |
  | bf16 (no AMX on this CPU) | 90 s | 0.3 |

  The model card's 14 pairs/s on a desktop CPU is for short benchmark passages. Our chunks are several times longer, so on CPU the spec's top 30 within 3 s is **not reachable** with this model: reranking is skipped (and the fused order kept) unless the reranker has a GPU (about 3,200 pairs/s on an H100, 980 on an RTX 3090 per the model card) or the work is reduced (fewer candidates, a smaller Ettin reranker: 68M, 32M or 17M, same code, only `CIQ_RERANK_MODEL` and the baked-in model change). int8 was rejected: it ran only through a path that does not reproduce sentence-transformers' scores, for a gain of under 2x.
- **Consequences:** the default stack does not start the reranker (`docker compose --profile rerank up -d`). Reranking quality for legal text with a general-purpose, English-only reranker is unmeasured; M9 onward should compare it with the fused order and with Voyage. The Voyage reranker adapter is not implemented yet.
