# ADR-023 — Vendor assessment and comparison: decisions made while building M13

**Status:** Accepted (V1)

The design is fixed by the spec (§21, §22.6, §22.7, §25.5): a fixed signal taxonomy, signals mapped from contract findings or read from documents, aggregation across documents, a pure scoring engine, model-written explanations that are validated, and a deterministic comparison with "not comparable" cells. These are the decisions the spec left open or where the implementation differs.

- **The model never scores.** Its output schemas (`ai/schemas/vendor.py`) contain no numeric field other than source numbers; a test inspects the JSON schemas to keep it that way. A signal's severity is a category the engine maps to a number. Scores, weights, coverage, completeness, rankings and the "provisional" flag all come from `analysis/vendor`, which imports nothing from `ai`, `db` or `api` (an import-linter contract).
- **Scoring follows §21.5 exactly**, with three decisions the spec did not state. (1) The severity bands are written as exclusive upper bounds in YAML (`low: 25, medium: 50, high: 75`), since the spec's interval notation is not YAML. (2) A dimension or assessment with no score has severity `info`, since the database columns are not nullable. (3) "Provisional" also applies when fewer than `min_assessed_dimensions` (4) dimensions were assessed, as the spec's formula says; the number is configuration. Hypothesis tests check: a favorable signal never raises a dimension's score; a riskier status never lowers it; extra gaps never change a score and only lower coverage; the order of documents does not matter; identical inputs give identical outputs; scores stay within the risks used; renormalised weights sum to one.
- **A quirk in the specified numbers, kept and recorded.** Aggregation orders readings as the spec says (any unfavorable outranks ambiguous outranks favorable), but the configured risk values put "unfavorable, low" (30) below "ambiguous" (50). So when one document is ambiguous and another is unfavorable-low, the aggregate is unfavorable-low and scores lower than ambiguous would. The monotonicity property is therefore stated over the risk values (10, 30, 50, 55, 80, 100), not over status names. If this matters, change `signal_risk` in `config/vendor/scoring_v1.yaml` (a new `semver`), not the code.
- **`conflicting` is not a gap reason.** The spec lists it among the reasons a signal can be missing, but its algorithm scores a conflict conservatively and includes it. A conflict is a flag on the signal (`conflict: true`), not a gap.
- **Extraction-sourced signals** are read per dimension with one structured call (five calls: legal has none; the graph still sends six branches and the legal one returns at once). An evidence-based status needs a valid citation and a rationale the cited passages support (the same check as chat and contract analysis). `absent` is accepted only if every document's text was extracted completely **and** the best rerank score is below the absence threshold; otherwise the signal is `insufficient_evidence`. A failed call or retrieval costs those signals, with a note on the assessment, never the whole assessment.
- **Explanations are validated, with a deterministic template as the fallback.** The model's reasoning is used only if it names no signal id outside its dimension and states no number the engine did not compute (every number in it must already appear in the context it was given). Mitigations must reference unfavorable or ambiguous signals of that dimension; others are dropped. If the model is unavailable or fails validation, a template built from the results is used and a note says so.
- **Dependencies (§25.5).** `VendorAssessmentService.start` starts the missing contract analyses itself (through `ContractAnalysisService.start`, so it never doubles one that is running) and records them as `params.depends_on`. The task asks the service to run; if a dependency is still `queued` or `running`, the service puts the job back to `queued` and the task calls `retry(countdown=30, max_retries=20)`: a bounded wait that holds no worker slot. After 20 waits the job fails `DEPENDENCY_NOT_READY` (a test plays this out with Celery's eager mode). A dependency that **failed** does not block: the assessment proceeds and treats that document's contract-based signals as `insufficient_evidence`, with a note. The graph also verifies, and fails `DEPENDENCY_NOT_READY` if a document has no current analysis at all.
- **"Current" analysis** means a succeeded job with the current ruleset version that finished after the document last changed. The same definition is used by the contract service (reuse) and the vendor store (dependency check).
- **One assessment at a time per vendor.** An active assessment is returned (200) rather than duplicated.
- **Persistence** is one transaction: the assessment, its six dimensions, their citations (stored with `risk_dimension_id`), the `is_latest` flip (the previous latest is demoted in the same statement sequence, so the partial unique index never sees two) and the job's success. Storing the same job again deletes its assessment first and inserts anew.
- **Comparison.** The preconditions are checked at start, each a 409 naming the vendors: no assessment (`ASSESSMENT_REQUIRED`), different or outdated configuration (`INCOMPATIBLE_ASSESSMENTS`, which also catches an assessment from a configuration older than the current one), and, with `require_fresh`, an assessment older than the vendor's newest document or contract analysis (`CONFLICT`). The graph checks them again, because the world can change between the request and the run. The comparison row is created at start with an empty result, so the 202 can return a `comparison_id`; the result fills in when the job succeeds.
- **What "comparable" means**, as built: a dimension only if every vendor was `assessed` with coverage at least 0.6; a signal only if every vendor has evidence for it (or all have the same absence). An absence is never ranked against an established clause unless the policy says absence is unfavorable, and then it is labelled "absent (treated as unfavorable by policy)". Ties give no leader. The ranking is suppressed with a stated reason if any assessment is provisional, any vendor has no overall score, or fewer than four dimensions are comparable.
- **The narrative** (100 to 350 words: the spec says 150 to 300, the check is a little wider so a good summary is not thrown away for being 140 words) is accepted only if it names no unknown id, does not compare anything marked not comparable (a keyword check over each sentence with a comparative word), and does not rank when no ranking exists. Otherwise the template summary is used and the job still succeeds; the note says why. The comparative-word list excludes "behind" and "ahead" alone, which gave a false positive on "the evidence behind each dimension"; "falls behind" and "ahead of" stay.
- **Not built:** the latest-assessment summary on `GET /vendors/{id}` (the spec lists it), per-signal evidence quotes in the history listing (it returns the summary), cross-document contradiction reasoning (V2), a Streamlit report page (M17), and comparing vendors assessed with different configurations (a re-run is the supported path).
