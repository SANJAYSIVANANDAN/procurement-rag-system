# ADR-020 — Conversation memory and persistence: decisions made while building M10

**Status:** Accepted (V1)

The design is fixed by the spec (§23, §24, ADR-005): a Redis session window per conversation, PostgreSQL as the source of truth, rebuild on any doubt. These are the decisions the spec left open or where the implementation differs.

- **Redis is a cache; losing it costs latency, never correctness.** The window is rebuilt from PostgreSQL (`memory/reconstruction.py`) whenever Redis has nothing, has the wrong thing, or has something that cannot be trusted. The reason is logged as `memory.rebuilt`. Reconstruction reads only completed messages after `summary_through_seq`, newest first, up to the token budget; anything older that is still unsummarised comes back as overflow and is summarised.
- **What counts as "cannot be trusted"** (each is tested against real Redis): no meta hash (miss or expiry); `schema_v` missing or different; `last_seq` different from `conversations.last_completed_seq` (a reply committed to PostgreSQL but never recorded in Redis); `summary_through_seq` different from PostgreSQL (a summary written to one store but not the other); a non-numeric meta field; a turn that is not valid JSON or does not match `SessionTurn`; turns out of sequence order; and a `window_tokens` that does not equal the sum of the turns' tokens. The last three go beyond the spec's list; they cost nothing (the data is already in hand) and catch half-written or hand-edited state.
- **`load` takes the conversation state, not just its id.** The spec's signature is `load(scope, conversation_id, query)`, but its own algorithm compares `meta.last_seq` with the conversation row "already loaded for the ownership check, so this costs no extra query". Passing that state in (`ConversationState`: id, `last_completed_seq`, `summary`, `summary_through_seq`) is what makes that true. The service checks ownership in PostgreSQL first and only then calls memory, so Redis is never touched for a conversation the caller does not own (tested: nothing is created or read for another user).
- **A session that expires while a reply is being generated is rebuilt, not restarted.** `record_turn` on a missing session would otherwise create a window holding only the last exchange, with a `last_seq` that looks right, so the check on the next load would pass and the earlier history would silently be gone. Instead it rebuilds from PostgreSQL, which already contains the exchange (the reply is committed before it is recorded).
- **Overflow and summarising.** After each exchange, turns are popped from the front while the window is over budget, always keeping the newest two (a window is never empty of the last exchange, even if that exchange alone exceeds the budget). Overflow is summarised in a background task so a reply never waits for it. The order is the spec's: the summary is written to PostgreSQL and committed first, then mirrored into Redis. A per-conversation lock makes summaries run one at a time, each building on the last, and `advance_summary` only ever moves `summary_through_seq` forward, so two summaries finishing out of order cannot regress it.
- **A failed summary drops the session instead of leaving a gap.** The popped turns are no longer in Redis, so if summarising fails the window would be missing them with nothing covering them. The session is deleted; the next load rebuilds from PostgreSQL, finds the same unsummarised turns as overflow and tries again. Tested with the provider down and then healed.
- **Serialisation is Pydantic's JSON, not `orjson`.** `SessionTurn` is validated with `model_validate_json` (Rust-backed) and written with `model_dump_json`; adding `orjson` would not change behaviour or speed meaningfully here. A turn's `ts` should be the committed message's `completed_at`, so a turn recorded live equals the same turn rebuilt; tests compare sequence, role, content and tokens for that reason.
- **All key strings live in `core/redis_keys.py`** (spec task 1), including the rate-limit, sweep and cache keys that earlier milestones had scattered. A test fails if a `ciq:` string appears in any other module. Session keys embed the user id, so two users cannot address the same session even with an identical conversation id.
- **The model port exists, the Anthropic adapter does not.** `LLMProvider`, `LLMRequest` and a scriptable `FakeLLMProvider` (spec 19.15) are defined because summarising needs them; the real adapter and the route configuration arrive with the chat graph in M11. For that reason the API container does not yet build a `MemoryManager` (production settings forbid the fake provider); `build_memory_manager` is ready for M11 to wire.
- **Conversation endpoints (spec 16.2):** create, list (keyset cursor on `(updated_at, id)`, `archived`), detail with documents, `PATCH` (rename, scope, archive, vendor; only fields sent change), and messages with citations (`before_seq` and a `next_cursor` that is the next `before_seq`). Conversations are archived, never deleted (FR-CHAT-2). Another user's conversation is a 404 on every endpoint.
- **Submitting a message is a service method, not an endpoint yet.** `ConversationService.submit_message` stores the user message and a pending assistant message in one transaction, with the next two sequence numbers allocated under the conversation row lock, `selected_document_ids` resolved (named documents, else the conversation's scope, else every ready document, always cut to the user's own ready documents), and an idempotent replay for a repeated `client_message_id` (including two racing requests, which store exactly one pair). The `POST .../messages` route that also starts generation belongs to M11.
- **Not built:** the stream and conversation-lock keys have builders but no users (M11); the stale-message sweeper (§24.2) and conversation-level memory for vendors; summaries are not yet limited per user for cost.
