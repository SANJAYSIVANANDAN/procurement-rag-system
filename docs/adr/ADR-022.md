# ADR-022 — Contract analysis: decisions made while building M12

**Status:** Accepted (V1)

The design is fixed by the spec (§20, §22.5): a YAML ruleset, per-rule targeted retrieval, heuristics, one structured model call per batch of rules, a deterministic status decision, a `Send` fan-out graph with a PostgreSQL checkpointer, and idempotent persistence. These are the decisions the spec left open or where the implementation differs.

- **The model proposes; code decides.** `analysis/contract/status.py` is pure. It takes the retrieval evidence, the heuristic hits, the extraction quality and the model's assessment and returns the status, severity, confidence and evidence sufficiency. A clause is `absent` only if extraction was complete, the search was weak or the model confidently found nothing, no clause tagged with a matching type exists, and no pattern hints it is there; otherwise it is `insufficient_evidence`. Every rule of the table in §20.5 has a test, including the boundaries.
- **A heuristic can only push towards risk.** The schema rejects an effect whose status is anything but `problematic`, and a clean scan never upgrades a clause: a rule that matches nothing and gets an unsure model answer stays `insufficient_evidence`. A forced red flag beats low model confidence and an unsupported explanation, because its evidence is the matched text itself, but a finding that is `problematic` still needs a cited passage.
- **Explanations are checked against what they cite.** The same overlap, number and quotation check that chat answers use (`CitationValidator.supports`, now public) runs on each explanation against the passages it cites; an explanation that fails makes the finding `insufficient_evidence` rather than shown as fact. Absences and could-not-assess findings are written from facts in code (what was searched, the best score, the pages scanned), never by the model.
- **Severity.** The rule's policy sets the base; heuristics can raise it. The spec also lets the model raise a severity by one level, but its `RuleAssessment` schema (§17.4) has no such field, so that is not implemented. `acceptable` and `insufficient_evidence` are `info`. Confidence and evidence sufficiency follow §20.7.
- **A structured-output schema with no free-form objects.** The spec's `extracted_values: dict[str, ...]` becomes a list of `{name, value}` pairs, because structured output needs a closed schema. Length limits are stated in field descriptions and enforced by truncation, so a reply that is a little too long is not thrown away.
- **Graph state is plain JSON.** It is checkpointed after every step, so ids are strings and models are dicts (`model_dump(mode="json")`), and errors are dicts. The owner's scope is rebuilt from the owner id by `scope_for`, supplied by the service, because graphs may not import `db`.
- **Per-rule failure, per-job threshold.** A batch the model cannot answer (after the provider's retries), or a retrieval failure, makes those rules `insufficient_evidence` with `details.error`; the job still succeeds. If more than 50% of the rules end in error the job fails with `ANALYSIS_DEGRADED` and stores nothing. Exactly half is tolerated.
- **Resume is real.** One checkpoint thread per job (`thread_id = job_id`). A run that finds an unfinished thread calls `astream(None)`; the tests kill a run after the batches and in the middle of them, and assert the finished batches are not asked of the model again. A finished job's checkpoints are deleted. The checkpointer opens a connection per run rather than the spec's shared pool of 1 to 4: one analysis is one long task, so a pool saves nothing.
- **A rerun is the claim's business, not the graph's.** Persisting marks the job `succeeded` in the same transaction, so a redelivered message finds a succeeded job, cannot claim it, and is skipped (tested). If a run did happen twice, persistence is delete-then-insert and leaves one set of findings.
- **`POST /documents/{id}/analyze`.** It checks ownership and `ready`, then never lets two analyses of one document run at once (an active job is returned, even with `force`). An analysis of the same ruleset version that finished after the document last changed is returned unless `force` is set. Otherwise a job is created with the key `contract_analysis:<document>:<n>`, where `n` is the number of earlier jobs: concurrent requests compute the same key and the unique index arbitrates. The row is committed before the task is published; a failed publish leaves a `queued` job that the reconciliation sweep re-publishes. A first version of this keyed on the count only, so a second request while a job was active created a second job; the test that asked twice found it.
- **Unusual provisions scan every chunk of the document**, not only the retrieved candidates, because an unusual clause is by definition one no rule searches for. At most three examples per pattern are reported.
- **Obligations are findings that are not judgements.** They are stored with `risk_category=obligations`, `severity=info` and `clause_status=acceptable` (the status column is not nullable and "acceptable" is the neutral value); the structured fields live in `details`. A deadline in days is kept only if that number appears in the cited text: a model that invents a number loses the number, not the obligation. The obligation pass is best effort: if it fails the analysis still completes, with a note.
- **Internal contradictions** are found deterministically (rules name a value to look for with a pattern: a payment period, a notice period, the governing law; two different values for one key in different passages make a pair) and a model confirms each pair, at most five per document. Only confirmed pairs become findings. The model is told to answer "no" when in doubt, since two numbers are often two different things.
- **Citations of a finding are numbered 1, 2, ... within that finding**; the per-rule source numbers the model saw (`C1`...) are internal to a batch.
- **Settings.** `config/rag.yaml` gains an `analysis` section (absent threshold, extraction-quality ratio, rules per batch, retrieval depth, degraded fraction, contradiction pair limit); concurrency is the existing `CIQ_ANALYSIS_MAX_CONCURRENCY`. The ruleset is validated at start-up (`get_ruleset()` in the API and the worker): a duplicate id, an invalid pattern, an unknown clause type or an unknown field stops the process.
- **Worker and platform notes.** The worker container now builds the model provider, the retrieval engine (no Redis cache) and the analysis runner; it needs `CIQ_CHECKPOINT_DB_URL` and a model key like the API. psycopg's async mode cannot use Windows' default event loop, so the worker runtime and the tests select the selector loop there.
- **Not built:** `unusual` and obligation passes are not individually switchable; the Streamlit report page (M17); comparing findings across analyses or documents (V2); and re-running only the rules whose passages changed.
