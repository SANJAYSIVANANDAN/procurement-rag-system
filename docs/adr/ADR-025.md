# ADR-025: SSE streaming: decisions made while building M15

**Status:** Accepted (V1)

The design is fixed by the spec (§26): a Redis Stream per reply, a publisher that coalesces tokens, a consumer that resumes from `Last-Event-ID` and replays from PostgreSQL, and an `sse-starlette` endpoint. These are the decisions the spec left open.

- **PostgreSQL stays the record; the stream is a courier.** A Redis error while publishing is logged (`stream.publish_failed`) and dropped, so the producer finishes and the reply is stored regardless. A listener whose events were lost gets the reply from PostgreSQL once the stream goes quiet. The alternative, failing the reply when Redis hiccups, would turn a display problem into lost answers.
- **Layering.** The spec puts the consumer in `streaming/`, and the import rules keep `streaming` away from `services`. So the consumer knows Redis and a `load()` callback that returns a `StoredReply`; the PostgreSQL side (ownership checks, the stored message and citations) is `services/stream_service.py`. Authorization happens before the response starts, so a wrong id is a plain 404 and not a broken stream.
- **A reconnect after the terminal event returns nothing.** Browsers reconnect when a stream closes. Without a check, a finished reply would keep replaying its end. The consumer looks at the stream's last entry: a terminal event the listener already saw ends the stream at once. (The first version of the resume test found this.)
- **Stall detection looks at PostgreSQL.** After `CIQ_STREAM_IDLE_TIMEOUT` of silence, a final message is finished from the database (terminal events only, with the last real id kept), and a message that is not final becomes `STREAM_STALLED`. The sweeper, not the consumer, marks the message `interrupted`, as in the spec; that takes up to the stale threshold (10 minutes).
- **Synthetic ids for a replay are `0-1`, `0-2`, ...** A replay resumes by its own ids. A client that arrives with a real Redis id after the stream expired cannot be placed in the replay, so it gets the whole replay; `message_start` tells it to reset and `message_complete.content` is the truth.
- **Token merging.** A merged token carries the index of its first token and the text of all of them. A timer task flushes a batch that has waited 30 ms. A per-message lock keeps flush order identical to publish order; a property test checks that text and order survive any pattern of tokens, pauses and status events.
- **Expiry.** A stream expires 600 s after its terminal event. A stream that never gets one (a dead producer) expires 3,600 s after its first entry, so keys cannot accumulate.
- **The conversation lock is still released by `ChatService`**, in the producer's `finally`, not by the publisher on the terminal event as spec 26.3 words it. The service already had to release it on every failure path (cancel, crash before any event); a second release path in the publisher would only add a way to release the lock twice. The release is a token-checked Lua script either way.
- **A dedicated Redis client for listeners.** `XREAD BLOCK` waits up to 15 s; the shared client's socket timeout is 2 s so that rate limiting and the lock fail fast. Listeners have their own client with a timeout of block + 2 s.
- **Not done:** a rate limit on the stream endpoint (the spec lists none; a reconnect storm is limited only by authentication), a per-user cap on concurrent listeners, and `timings_ms` in a replayed `message_complete` (they are not stored with the message, so a replay has `{}`).
